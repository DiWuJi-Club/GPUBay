- **`SPARK_TRUST_PROXY`**：platform 在反向代理之后时必须设 `SPARK_TRUST_PROXY=true`，多层代理再设 `SPARK_TRUSTED_PROXY_HOPS`。否则「同 IP」标记与邀请码查询限流（每 IP 每分钟 60 次）看到的都是代理地址：每个绑定都会带「同IP」，所有访客共用一个查码额度。
- **`SPARK_PUBLIC_BASE_URL`** 必须是用户可访问的控制台地址，邀请链接据此生成。
- **多副本滚动窗口**：滚动发布期间，旧副本不认 `invite_code`，窗口内注册的用户不会绑定。一次性停掉全部副本再发布即可消除这个窗口。
- **法务**：帮助页与邀请页的规则文案（返利不可提现、平台有权撤销异常返利）。
- **财务**：
  - 线下退款的核算口径（R4）：按「充值净额 − 消费」核算，返利部分不退。后台用户详情的「邀请」区块显示累计发放净额。

  - 页面上的「本月返利（已到账）」是到账毛额，「累计净返利」含抵欠账部分，两者都不等于钱包的实际净入账（验收观察 5）。

## 已知限制
- **超长事务**：一个写 `order` 流水的事务如果开着超过 62 分钟才提交（1 小时回看 + 2 分钟滞后），它的流水可能落在发现窗口之外而漏扫。用后台「重扫」把水位拨回 N 天即可补上，因为 `source_ledger_id` 唯一，重扫不会重复计提。正常事务只有几秒。
- **NAT 下普遍带「同IP」**：同一 NAT 出口（家庭、公司、校园网）的每个绑定都会带「同IP」。R8 规定这个标记只提示、不搁置。后台列表不要把它当作「可疑」的默认筛选。
- **`identity.AdminListUsers` 的 LIKE 没有转义**（计划 4 起就存在）：搜索词里的 `%`、`_` 会按通配符匹配。只影响后台用户搜索的结果范围，没有注入风险（参数化）。referral 自己的搜索已经转义。
- **e2e 清扫钩子**：`/hooks/sweep` 先拿进程内互斥，再在专用连接上拿 `pg_advisory_lock(rental.SweeperLockKey)`（Task 17 已处理），否则两个重叠的 `Rental.Sweep` 会在 `fleet.MarkOfflineStale` 上自己死锁。生产环境由 `RunSweeper` 的同一把咨询锁保护。`MarkOfflineStale` 已改为按 id 顺序锁候选行并跳过别的事务锁着的行（`FOR UPDATE SKIP LOCKED`）：合并计划 7 后的 `make check` 里，`TestReferralConcurrentFundsConsistent` 出现过一次它与锁机器行的业务事务形成的三方死锁，修复后清扫一侧不再等待。
- **没有 `TestInvariantsAgainstDevDB`**：规格 §16.4 第 12 项要求的、连开发库只读执行的用例没有实现。验收时用临时工具做了等价的只读调用（`CheckInvariants`），结果 OK。建议改为加一个 CLI：`platform referral check-invariants`，供生产库只读核对。不过 `CheckInvariants` 第 4 条要求静止态（没有待处理流水），在生产库执行前要等一轮清扫，或者改为只检查 `created_at < now − 1h` 的流水。
- **永久跳过的流水**：
  - 扣款对应的订单查不到时，先暂时跳过：钉住水位，每轮都会在日志里记 Error。过了 `SkipGrace` 后写 `void` 占位。
  - 该订单的退款随后走「无 reward」占位。
  - 一直处理失败的行（真实错误）会一直钉住水位。每轮重扫的窗口随之变大，但结果正确，并且 25 小时后告警。
- **`X-Device-Id`** 只是 localStorage 里的 UUID：清缓存或用隐私窗口就会换新。规格已接受。后端只在登录和控制台 `GET /me`（会话启动补记，终审 I1）时记录它；后台页面也会发送并保存 `sc_device`，后台接口忽略它。
- **落地页多一跳**：`/?ic=…` 落地后先 `replace` 到 `/market?ic=…`，再去掉参数（约 1 秒，验收观察 2），功能正确。
- **退款触发的扣回要等下一轮清扫**（≤ 1 分钟）才在明细和钱包里出现。后台退款成功的提示没有说明这一点（验收观察 6）。
- **`ErrInviteCodeInvalid`、`ErrReferralFrozen` 两个错误码已定义但没有使用**：原因放在登录响应的 `invite.reason` 里。

## 负责人裁定（规格 §1.3，默认值，可推翻）
- R1：返利比例 10%，按被邀请人实付租用金额（扣除退款）计算，向下取整到分。
- R2：返利期 12 个月（从绑定时起算）；绑定本身永久保留。
- R3：单个被邀请人累计 ≤ ¥500；单个邀请人 30 天内发放 ≤ ¥5,000；超出部分记 `capped`，不补发。
- R4：返利进钱包余额，不可提现、不可转让；线下退款按「充值净额 − 消费」核算，返利部分不退。
- R5：`settle_after = max(扣款 + 7 天, 预订开始时刻)`。发放前退款只改数字；发放后退款要扣回，余额不足记欠账。
- R6：邀请人必须已实名才发放；未实名时返利保持待发放。
- R7：只在注册时绑定；邀请码在 localStorage 存 30 天；老用户带码登录不绑定。码无效或码主被冻结时，注册照常成功，响应里给出原因。
- R8：同设备 → 搁置；同身份 → 撤销；同 IP（24 小时内）和爆发（24 小时内 ≥ 20 个绑定）只打标记。
- R9：后台对搁置的绑定可以「通过」或「撤销」（撤销时待发放全部作废，已发放的不自动扣回）。冻结邀请人后，码不可再绑定、返利停发但继续累计，解冻后恢复。
- R10：不发短信、不做站内信；「我的」页显示本月返利入口。
- R11：邀请页需要登录；未实名也能看到码，页面提示实名；被邀请人只显示脱敏手机号。
- R12：邀请码不可自定义、不可更换。
- R13：返利流水在钱包里显示为「邀请返利 / 返利扣回」，备注里写脱敏手机号和订单号。
- R14：费率版本的 `effective_from` 必须 ≥ 提交时刻；首个版本由迁移写入。

## 实施中确定的产品行为（裁定）
- **迁移编号与发布顺序**：迁移改为 `00021`（计划 7 先合并并占用 `00020`）。计划 8 只在计划 7 合入 `main` 后合并。开发平台验收（Task 18）在独立的全新 PG（5434）和非默认端口上进行，不碰开发库 `:5433`。
- **登录**：
  - `identity.Login` 签名不变，新增 `LoginWith`。`identity` 导入 `referral` 的类型，`referral` 不导入 `identity / rental`。
  - UA 统一由 `referral.SanitizeUA` 在 `Bind` 内清洗，`identity` 传原始 UA，避免非法 UTF-8 让注册回滚。
  - 垃圾邀请码 → `invalid_code`，不报错。`invite_code` 超过 32 字节或不是合法 UTF-8 时，按无效码处理，不截断。
  - `X-Device-Id` 只有 UUID 形态时才记录，并传给 `Bind`。
- **锁顺序**：
  - `Bind` 先对码主的 `users` 行加 `FOR KEY SHARE`，再锁 `referral_accounts`，否则与码主本人的实名事务反向而死锁。
  - 所有写 rewards 或钱包的路径，都先对 `users` 加 `FOR KEY SHARE`，再锁账户。
  - 计提和退款在账户锁之后复查「已处理」。`processRow` 把撞 `referral_events_source_uniq / referral_rewards_pkey` 视为并发已处理。
- **实名钩子**：
  - 实名钩子永远不让实名失败。钩子出错时重试一次；仍失败就写审计 `referral.kyc_check_failed`，实名照常通过。
  - 同身份判定比对邀请人和被邀请人的**全部** verified 指纹（不只最新一条）。
- **发放（Release）**：
  - 发放前复查同身份：比对邀请人，以及同一邀请人其它未撤销的被邀请人。命中就撤销，不发放。
  - 邀请人或被邀请人有未解决的 `kyc_check_failed`（时间晚于 `COALESCE(reviewed_at, bound_at)`）时，绑定转 `held`（`hold_reason='kyc_check_failed'`），由后台审核解决。后台的 approve 或 revoke 会写 `reviewed_at`，视为已解决。
  - 用 SQL 预筛，加上轮内游标翻页，防止被门槛挡住的行饿死后面的行。
  - 重放保护先于抵欠账执行。
- **退款与发现**：
  - 退款可以先于计提落地：没有任何事件的订单延后处理；已有 `capped / void` 占位的订单写 `refund(0)` 占位。
  - Discover 同一批里先处理 `order_pay`，再处理 `refund`。
  - 跳过或失败的行钉住水位，过了 `SkipGrace` 写占位，卡住 25 小时告警 `referral_scan_stuck`。
- **费率版本**：`effective_from` 允许 5 分钟的「过去」容差（表单提交延迟），但落库时钳到提交时刻，不会追溯生效（R14）。
- **后台**：
  - finance 可以撤销绑定（需动态码），按规格 §10.2 和路由 `financeRoles` 实现，没有采用「finance 只读」。
  - 重扫有行失败时返回 200 和 `{failed: n, incomplete}`：重扫已经生效，动态码窗口照常打开，不返回 500。
  - 后台「邀请人」列表默认按累计发放净额降序。
- **控制台文案**：
  - 「累计净返利」= 已发放 − 扣回，含抵欠账部分。
