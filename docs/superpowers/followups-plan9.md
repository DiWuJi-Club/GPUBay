# 计划 9 遗留事项

来源：计划 9 设计（2026-10-24）§1.3、§1.4、§17，实施过程，以及真机验收检查点 A / B（`acceptance-plan9.md`）。均不阻塞合并。实施期间的裁定见规格 §1.4（I1～I17），本文不重复。

## 上线前需要核对（规格 §17）

- **首批模型清单与定价**（运营）：模型、价格（元 / 百万 token）、`default_max_tokens`、`max_output_tokens`、副本数。验收用的是 `Qwen/Qwen3-4B`，输入 ¥0.50 / 输出 ¥1.50。
- **池机器数量**：池里的机器数应 ≥ 全部上线模型的副本数之和，否则告警 `llm_pool_short`。池内机器永不出租，从出租机组划机器进池要和运营的可租台数一起评估。
- **操作顺序：先把机器加入池，再上线模型**（检查点 A 观察 O-2）。反过来做，模型上线的那一刻池里没有空闲机器，Controller 会立即发一条 `llm_pool_short`；机器随后入池、节点照常建好，但告警按平台惯例要人工处理，不会自动关闭。README 已按这个顺序写。
- **多副本部署**：`SPARK_LLM_GATEWAY` / `SPARK_LLM_CONTROLLER` 的配置。推荐用户 API 单副本、两个开关都 on；必须多副本时，只在一个副本上开网关并把 `/v1` 路由到它，或者多个副本都开网关、把后台用户限额按副本数折算（README「Token 商城」一节）。
- **计费说明文案**（法务）：帮助页「Token 商城」一节、控制台快速开始的说明、结算与欠费的提示。
- **`vllm-node` 的 NGC 标签复核**：与计划 7 相同，验收用 `25.09`（vLLM 0.10.1）；`--task embed` 等参数与这个版本绑定，换标签要在真机上复测对话、流式、向量三类模型。
- **默认限额**：每用户 RPM 60 / TPM 200,000 / 并发 8、单节点并发 32 是否调整。
- **连接池**：`SPARK_DATABASE_URL` 加 `pool_max_conns=20`（README「数据库连接」）。检查点 A 的缺陷 A-1 已修，迁移连接也能识别这个参数。
- **应用导入**：已有部署升级到计划 9 时执行 `platform admin app import deploy/apps`。检查点 A 的缺陷 A-2 修复后，内容相同的已有版本会跳过，不再整体失败；随后在后台发布 `vllm-node`（super + 动态码）。

- **Token 消费计入邀请返利**：计划 8 的返利基数只有 `order_pay`，`llm_pay` 不计入（见 `followups-plan8.md`「规格列出的遗留」与计划 8 规格 R1）。如果以后要计入，要改 referral 的发现查询与 R1 的口径，并处理 Token 消费没有「订单退款」这条扣回路径的问题。
- `api.<domain>` 独立子域；按 Key 的 IP 白名单；Key 的只读 / 作用域细分。
- 跨机张量并行、一机多模型、按负载自动伸缩副本（现在由运营手动设副本数）、按时段预热节点。
- **洗机时保留模型缓存**：节点释放走 `ReleaseSystem` → 洗机，数据盘上的模型随之清除，下次建节点重新下载（Qwen3-4B 约 7.6 GB，检查点 A 下载约 4 分钟，检查点 B 约 4 分钟）。要保留缓存需改 Agent 的 wipe 语义，与计划 7 遗留的「机器级共享模型缓存」（`followups-plan7.md`「规格列出的遗留」）是同一件事，应一起设计。

- 日志内容留存、内容安全审核、敏感词过滤；按请求的审计导出。
- 用量预警短信 / 邮件、余额低于阈值提醒；站内信。
- Prometheus 指标导出（请求数、TTFT、吞吐）；节点 GPU 利用率采集（Agent 已有 `last_metrics`，可后续接入）。
- `/v1/responses`、`/v1/audio/*`、`/v1/images/*`、`/v1/files`、批处理接口；函数调用之外的扩展字段校验。
- 后台「一键把 N 台空闲机器加入池」、按机组批量入池。
- 节点级日志实时流（现在复用计划 7 的部署日志尾部）。

## 已知的软约束（实现如此，上线时知晓即可）

- **限额与在途计数是进程内的**（T15）：RPM / TPM / 并发、节点在途数、Controller 排空看到的在途请求都只在本进程内。多副本时各算一份，见上面「多副本部署」。
- **鉴权缓存 30 秒**：Key 的鉴权结果（含用户状态、实名状态、余额与欠费的快照）缓存 30 秒。同一进程内撤销 / 停用 Key、调额度、结算、后台封禁 / 解封会立即让缓存失效（I8；封禁 handler 调 `LLM.InvalidateUser`），但以下变化最多 30 秒（`llm.KeyCacheTTL`）后才生效：在另一个进程里做上面这些操作；实名状态变化（企业认证 / 实名审核不调失效接口，Key 鉴权仍按缓存里的旧实名状态放行或拒绝）。
- **月上限与预算预检是软的**：Key 的月消费上限、余额预检都基于缓存加上本进程在缓存加载后记下的费用（I12）。并发请求、多进程、或实际输出超过估算时可以超出，超出部分照常计费（月上限超出后下一次请求才 429；余额打穿记欠费，由结算兜底）。
- **在另一个进程里封禁**：后台 API 与网关不在同一进程时（后台独立部署或多副本），封禁用户后网关最多 30 秒内仍接受该用户的请求；这段时间的用量照常计费。同一进程内封禁立即生效（检查点 A 第 8 项同理验证了停用 Key）。
- **只靠 e2e 钩子造出的节点不能重建**：`/hooks/llm/node` 直接插 `ready` 节点、不建部署，后台「重建」对它无效（没有部署可 Redeploy）。只影响测试环境。
- **欠费只能在 `max_tokens` 缺省或估算偏低时出现**（检查点 A 缺陷 A-3）：带 `max_tokens` 的请求，预检估算就是费用上界，且「预检 + 登记在途估算」在同一把锁内完成，并发也不会超额。实际欠费来自：不带 `max_tokens` 而输出超过模型的 `default_max_tokens`（规格 §5「不改写请求」），或提示词 token 数明显多于 `len(body)/3`，或多进程各自预检。
- **429 / 402 / 401 / 403 拒绝的请求不写 `llm_usage`**（检查点 A 观察 O-7）：控制台请求日志与后台用量里看不到被限流或余额不足拒绝的请求，只有网关选不到节点的 503 记为 `no_node`。需要排查「为什么被拒」时只能看客户端收到的错误体。

## 可以继续延后

- 检查点 A 观察 O-1：Qwen3 默认开思考模式，`max_tokens` 太小时 `</think>` 之前就被截断，vLLM 把整段放进 `content`。帮助页 / 快速开始可以提醒「推理模型请给足 `max_tokens`，或在提示词里加 `/no_think`」。
- 检查点 A 观察 O-6：Key 的 `model_slugs` 只接受非草稿模型，而草稿只能先上线才能下线；想预先给用户开「只允许某个新模型」的 Key，要先把该模型上线。
- 检查点 A 观察 O-8：`vllm-node` 默认 `GPU_MEMORY_UTILIZATION 0.85`，4B 模型也占约 100 GB 统一内存（大部分是 KV cache）。一机一模型时无妨；小模型想省内存可在模型的节点参数里调低。
- 检查点 A 观察 O-9：只补欠费、没有新用量的结算，流水备注是「Token 消费欠费补扣」，规格清单第 7 项写的「含欠费」只对同时有新用量的结算成立。清单措辞随 A-3 一起改。
- 其余检查点 B 的页面观察（日志尾部的 ANSI 颜色码、系统账号在部署列表 / 档期里显示为用户 ID、后台用量明细表在 1440 宽度下要横向滚动才能看到「费用」等）见 `acceptance-plan9.md` 检查点 B。

## 与计划 7 / 8 遗留的交叉引用

- 计划 7「机器级共享模型缓存」= 本计划「洗机时保留模型缓存」，见上。
- 计划 7 观察 O-6（容器内 vLLM 日志打印 `api_key`）：节点 vLLM 的密钥经环境变量 `VLLM_API_KEY` 传入，不进 argv（I6），检查点 A 在 `/proc/<pid>/cmdline` 与部署日志尾部都查不到节点密钥。
- 计划 8 返利基数只含 `order_pay`：Token 消费不产生返利，见上。
- 计划 8「没有 `TestInvariantsAgainstDevDB`」：计划 9 实现了 `internal/llm` 的 `TestInvariantsAgainstDevDB`（设 `SPARK_DATABASE_URL` 时连库只读核对，不设时跳过），检查点 A / B 都用它核对过真机数据。计划 8 的返利不变量仍可照此补一个。
